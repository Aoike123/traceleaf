# Git 提交规范

- 状态：项目约定
- 适用范围：人工与 Agent 创建的 Git commit

## 1. 标题格式

```text
<type>(<scope>): <中文动作与结果>
```

例如：

```text
docs(architecture): 明确同根任务树串行交接规则
feat(context): 按检查点重建任务上下文
fix(runtime): 阻止过期执行者提交任务结果
```

使用英文类型和模块名，中文描述变更。标题采用 ASCII 冒号，冒号后留一个空格。跨多个模块且没有明确归属时允许省略 scope：

```text
refactor: 统一 CLI 与桌面的任务控制接口
```

标题尽量控制在 72 个字符以内，直接写改变了什么，不加句号、日期、作者、表情或任务阶段编号。不使用“更新一下”“修复 bug”“完成阶段一”“优化代码”等无法识别实际变化的描述。

## 2. 提交类型

| type | 使用场景 | 示例 |
| --- | --- | --- |
| feat | 新增可使用的能力或行为 | `feat(cli): 支持查询任务状态与停止原因` |
| fix | 修复已有行为中的缺陷 | `fix(storage): 避免重复登记同一产物版本` |
| docs | 修改计划、架构、规范或使用说明 | `docs(plan): 拆分 CLI 模块与阶段验收` |
| refactor | 调整内部结构，预期外部行为不变 | `refactor(tools): 分离工具描述与执行适配器` |
| test | 新增或修改测试与测试夹具 | `test(recovery): 覆盖外部写入后进程退出场景` |
| perf | 针对明确性能问题实施改进 | `perf(context): 减少重复读取未变化的产物内容` |
| build | 构建、打包、依赖及工程工具链 | `build(desktop): 配置 Electron 应用打包` |
| ci | 自动化检查、构建与发布流水线 | `ci: 增加类型检查与核心测试` |
| style | 仅格式变化，不改变行为 | `style(core): 统一源文件格式` |
| chore | 其他维护工作 | `chore(repo): 忽略本地数据库与运行产物` |
| revert | 撤销已有提交 | `revert(runtime): 撤销任务恢复策略变更` |

一次提交同时包含功能与必要测试时使用 feat 或 fix，不额外拆出只能与该功能一起成立的测试提交。perf 的正文记录测量依据；没有测量时不宣称已获得性能收益。

## 3. 模块名

以下是推荐 scope，不要求提前创建对应包。新增模块时可以扩展，避免同一模块出现多个同义名称。

| scope | 范围 |
| --- | --- |
| repo | 仓库规则、目录与通用维护 |
| plan | 项目路线、阶段、实施清单 |
| architecture | 系统架构和执行语义文档 |
| contracts | 契约、Schema、领域错误 |
| core | 跨多个核心模块的公共基础 |
| runtime | TaskRunner、Loop、步骤推进 |
| scheduler | 执行权、父子交接与唤醒 |
| context | 上下文构建、快照与检查点 |
| capabilities | Skill/Tools 搜索、版本与装配 |
| gateway | 模型调用、限流、重试与归一 |
| tools | ToolExecutor、本地/HTTP/MCP 执行适配 |
| storage | SQLite、迁移、查询与事务 |
| artifacts | 文件产物、版本与来源 |
| recovery | 中断恢复、未知操作核对 |
| validation | 程序检查与 Jev/Laya 评审 |
| budget | 用量、预留、结算与限制 |
| environment | 凭证、执行环境与资源范围 |
| observability | 日志、事件追踪与系统评测 |
| cli | 命令、终端输出与退出码 |
| desktop | Electron 生命周期、IPC 与打包配置 |
| ui | React 视图与交互 |
| workflow | 流程定义、提取、校验与执行 |
| world | 后续领域状态与 RAG |

按变更主要目的选 scope，不罗列多个模块。文档可以使用其描述的模块，例如 `docs(cli)`；技术栈整体调整可使用 `docs(architecture)`。

## 4. 正文模板

简单、低影响的提交可以只有标题。涉及设计取舍、状态恢复、权限、数据迁移或性能的提交，应说明原因、实际改动和验证。

```text
<type>(<scope>): <中文动作与结果>

原因：
<为什么需要这次变更>

变更：
- <具体改变>
- <必要的兼容性或迁移说明>

验证：
- <实际执行的检查及结果>
- <未执行的必要检查及原因；无此项可省略>
```

正文记录已经发生的事实。不把计划中的测试写为通过，不把设计文档写成已经实现的功能。只有文档变更时，说明检查了哪些链接、格式或一致性，不笼统声称运行时测试通过。

## 5. 不兼容变更与撤销

改变已发布的命令参数、Workflow IR、接口契约或数据兼容性时，在 type/scope 后加 `!`，并在正文记录影响与迁移方式：

```text
feat(workflow)!: 将输入绑定改为显式产物引用

BREAKING CHANGE: 旧版 Workflow 需要迁移输入绑定字段；执行器拒绝未迁移版本。
```

设计阶段的一般文档修订不自动视为不兼容发布。数据库迁移也不一律加 `!`，按实际对使用者的兼容性影响判断。添加该标记不代表已经实现自动版本发布。

撤销提交可保留 `git revert` 自动生成的信息，并补充撤销原因；手工编写时应记录被撤销提交的 SHA。已共享的历史优先通过新提交修正，不为调整话术随意重写。

## 6. 提交粒度与流程

- 一次提交围绕一个可说明、可审查、可回退的目的组织。
- 相关代码、必要迁移、测试与说明可以放在同一提交。
- 大功能按可验证的步骤提交，不按“每编辑一个文件”拆分。
- 不提交密钥、SQLite 运行数据库、日志、上下文快照或大型生成产物；可复用的脱敏夹具和 Workflow 定义可以提交。
- 提交前查看 diff 与暂存内容，只加入本次工作的文件或片段，避免混入用户其他改动。
- 使用结构化工具参数，或准备正文文件传给 `git commit --file`，保留中文与真实换行。

第一版只采用文档约定，暂不增加 commitlint、Git hook 或自动版本发布依赖。后续如果需要强制校验，再统一配置工具；命名约定本身不保证这些工具可以解析所有中文标题。

## 7. 当前文档基线的建议话术

以下仅为建议，本规范不执行 Git 提交：

```text
docs(plan): 建立桌面优先的架构与分阶段实施基线

原因：
将已确认的 Traceleaf 设计整理为可持续维护的实施依据。

变更：
- 明确同根任务树串行交接、独立上下文与可靠恢复语义
- 确定 Electron、TypeScript 和 SQLite 的技术方向
- 拆分项目计划、架构、技术选型、地基清单与 CLI 模块计划
- 约定 Git 提交格式与模块命名

验证：
- 本地文档链接、代码围栏与行尾空白检查通过
- 文档记录设计目标，未实现或验证运行时代码
```
