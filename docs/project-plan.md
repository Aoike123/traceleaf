# Traceleaf 项目计划书

- 更新日期：2026-10-17
- 状态：设计计划，尚未开发
- 配套文档：[体系架构](architecture.md) · [技术选型](tech-stack.md) · [地基实施清单](foundation-plan.md)

## 1. 项目目标

Traceleaf 是一个桌面优先、可恢复、可追踪、上下文隔离的递归任务运行时。每个 Task 聚焦一个明确问题，按需装配 Skill 与 Tools，通过明确结果与证据返回父 Task。

同一根任务树仅一个节点活跃。父任务委派后挂起，子任务交付后父任务恢复，逐步推动整体目标完成。任务树随执行生长，不要求开始前生成完整计划。

长期链路：递归探索 → 验证成果 → 记录依赖 → 提取并参数化 Workflow → 新输入验证 → 版本化复用 → 未来由 Storyloom 等产品消费。

## 2. 已确认的产品约束

| 约束 | 含义 |
| --- | --- |
| 本地桌面优先 | CLI 先验证，Electron 后封装；网页不是首版前提 |
| 同根串行 | 不自动识别安全并行，不引入并行审批门禁；不同根任务并发暂不承诺 |
| 单 Loop 有限 | 限制步数、时间、费用与重复失败 |
| 大任务可持续推进 | 不以固定深度或节点数默认终止；额度不足可保存进度并暂停 |
| 拆解要求进展 | 子任务有明确输入、交付与完成条件；Loop 耗尽不自动递归 |
| 上下文独立 | 父子通过显式输入、产物和证据交接，不自动共享完整历史 |
| 能力版本稳定 | 优先在创建任务时装配；动态申请后续增加 |
| 验证有证据 | 程序检查优先，决策模型辅助；模型自述不等于完成 |
| 恢复考虑外部副作用 | 结果未知时先核对，不承诺端到端恰好执行一次 |
| Workflow 与聊天解耦 | 导出流程不依赖原探索会话，TS 执行器调度实际计算工具 |

用户可设置总体费用上限和截止时间。结构允许持续递归，不意味着每次执行或本机资源没有限制。暂停、取消与运行故障均保留已完成成果和可解释记录。

## 3. 推进方法与顺序依据

按已经讨论的模块顺序构筑，每个模块先独立验证，再接入后续模块。CLI 是验证入口，不决定核心开发顺序；首个交付是独立 ModelGateway，不是完整单 Task 系统。

阶段 1–12 对应基础与递归运行时模块，阶段 13–17 对应产品化与扩展。日志、基础 Schema、状态记录和安全检查在依赖它们的模块中先提供最小实现，后续专门阶段再完成系统化能力。例如阶段 3 需要最小上下文组装，但完整上下文管理在阶段 9；阶段 1 记录调用用量，整棵任务树的预算策略在阶段 7。不能以“后面才做”为由省略当前模块的必要正确性保证。

契约随模块一起明确，最后统一校验接口一致性，不先设计所有未来字段。阶段 4 先用脚本化拆解验证调度，阶段 8 再实现模型驱动的拆解与进展判断。

所有文档复用下表编号；CLI 命令与验收见 [CLI 模块计划](cli-plan.md)。工作量在网关阶段完成后按实际进度估算，当前不承诺总工期。

## 4. 完整构筑顺序与阶段验收

| 阶段 | 模块 | 交付与验收 |
| --- | --- | --- |
| 1 | ModelGateway | 独立调用接口与生命周期；结构化输出、Tool Calling；限流、受控重试、超时、取消、用量与未知费用记录。用薄 CLI、假提供商和一个真实提供商验证，不依赖 TaskRunner、任务树或完整数据库模型。只返回工具提议，不执行工具。 |
| 2 | 能力注册与装配 | ToolRegistry、SkillResolver、CapabilityBinder、MCP Client 与执行适配器；固定版本、范围授权、参数与资源版本检查。独立验证发现、装配、调用和观察，不要求模型自主循环。 |
| 3 | 单 Task Agent Loop | TaskRunner 串联网关、最小上下文与工具执行；自主选工具、观察、有限自愈、步数停止和候选结果交付。使用固定能力与受控任务验证，不引入父子树。 |
| 4 | 任务调度与父子协作 | 同根唯一活跃节点、父任务挂起、子任务执行、结果交付与父恢复；以脚本化委派验证 A 返回父任务后再运行 B，不自动调度并行。 |
| 5 | 持久化与执行恢复 | 补齐 SQLite 任务状态、执行权、检查点、过期提交保护、未知操作核对和幂等返回。注入进程退出验证不盲目重复写入；早期调用和操作记录接入统一存储。 |
| 6 | 结果交付与验证 | 统一结果包、完成条件、证据与程序检查；评审后端可接 Jev/Laya，用领域样本验证。工具成功或模型自述不能直接使任务成功。 |
| 7 | 预算与运行限制 | 将已有用量记录汇总为树级账本，完善预留、结算、未知费用、单 Loop 限制及用户整体上限。额度不足暂停续跑，不以固定深度或节点数默认终止大任务。 |
| 8 | 任务拆解与进展判断 | 将脚本化委派扩展为模型驱动的目标、输入、能力、交付与完成条件设计。识别同义递归；Loop 耗尽按原因选择补资料、换方案或拆解。 |
| 9 | 上下文构建与产物管理 | 补齐上下文分层、能力稳定前缀、按需读取、长结果外置、快照、检查点压缩和重建；父子仅显式交接。重建保留事实来源、不确定性与未确认操作。 |
| 10 | 执行环境与资源保护 | 完善凭证服务、文件/服务范围、进程或沙箱适配、资源版本与写操作保护。早期已有基本权限检查；本阶段验证实际隔离边界，特别是远程 MCP 的服务端权限。 |
| 11 | 可观测与系统评测 | 将早期事件与用量组织成完整轨迹，关联模型、工具和产物；建立固定基准、故障注入和版本对照。运行时验收与系统评测分开。 |
| 12 | 用户控制与运行入口 | 将已有安全停止、恢复机制接为稳定启动、查询、暂停、恢复、取消、输入补充接口；明确已接收/已完成、目标变更和非交互行为。CLI 提供完整控制。 |
| 13 | Electron 桌面封装 | React 界面、受控 IPC、独立核心进程；复用已有控制服务。验证安装、数据路径、迁移、关闭窗口与退出重启语义。 |
| 14 | 真实业务基准线路 | 在已有 MCP 基础上，用 blender-vse 跑通限定字幕场景，验证实际工程、版本冲突、恢复和证据。不是此时才首次连接 MCP。 |
| 15 | Workflow 提取与执行 | 人工辅助起步，裁剪轨迹、显式依赖、参数化、版本化 IR 与自有 TS 串行执行器；新输入和故障验证后才发布。 |
| 16 | World Engine / RAG | 依据具体领域需求实现来源、时间/分支、叙事或空间查询和评测；通过工具装配接入，和运行状态分离。 |
| 17 | Storyloom 集成 | 以稳定 Workflow 输入输出和运行控制契约集成业务；Storyloom 当前仍独立。 |

阶段不等于必须创建独立服务或独立包。模块复用同一核心，按可验证职责推进；后续阶段不能未经记录重新改变前面已确定的执行语义。

## 5. 递进里程碑

| 里程碑 | 覆盖阶段 | 可演示成果 |
| --- | --- | --- |
| M1 网关成立 | 1 | CLI 发起两种模式的请求，观察归一结果、限流退避、失败与用量 |
| M2 单 Agent 成立 | 2–3 | 装配固定能力，模型自主调用工具并有限自愈 |
| M3 可恢复任务树 | 4–5 | 父挂起 → A 交付 → 父恢复 → B 执行；关键位置退出后安全恢复 |
| M4 基础运行时完整 | 6–12 | 证据验收、预算暂停、有效拆解、上下文隔离、资源保护、轨迹与控制 |
| M5 桌面真实案例 | 13–14 | 无需终端完成真实工程任务，展示进度、费用、验证与恢复 |
| M6 Workflow 复用 | 15 | 离开原聊天历史运行新输入，比较探索与固化的成本、耗时和模型调用 |
| M7 领域业务链路 | 16–17 | 有评测依据的世界状态查询与 Storyloom Workflow 消费 |

M1 不要求字幕工程、两个业务工具、TaskSpec 或完整任务数据库。M2/M3 使用受控工程优先验证运行时，真实提供商与 MCP 的协议适配按阶段 1/2 提前验证。地基清单细化阶段 1–5，随后按对应模块继续补充。

## 6. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 拆解无进展 | 比较目标、输入、方法与交付变化，返回父任务调整 |
| 上下文增长与缓存下降 | 任务内版本稳定；长结果外置；在检查点重建并保留来源 |
| 评审模型误判 | 明确问题与证据，领域样本校准；保留程序检查与人工核验样本 |
| 写入成功但回包丢失 | 操作 ID、幂等或状态核对；无法确认时暂停 |
| 资源被外部修改 | 写入前检查资源版本；树内串行不代表环境静止 |
| 桌面数据库或产物损坏 | 短事务、一致性备份、迁移记录、内容哈希与孤立文件核对 |
| 界面或数据库阻塞 | 运行进程与界面分离；测试驱动行为，测量后优化 |
| 平台打包不兼容 | 尽早验证依赖与 Electron ABI，阶段 13 明确支持平台 |
| Workflow 过度泛化 | 新输入、失败路径与版本依赖验证后发布 |

## 7. 暂缓事项与扩展条件

- 动态能力申请：创建时装配稳定后再做，区分授权、当前工具与历史残留。
- World Engine / RAG：先确定具体查询、事实来源、时间/分支语义和评测集。
- Storyloom：保持独立；Workflow 契约与执行稳定后再集成。
- 云服务、PostgreSQL、队列：出现明确远程、多用户或派送需求后单独规划。
- Rust：原生需求或测量到的计算瓶颈出现后评估，不预先重写执行器。
