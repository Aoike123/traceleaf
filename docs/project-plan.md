# Traceleaf 项目计划书

- 更新日期：2026-10-16
- 状态：设计计划，尚未开发
- 配套文档：[体系架构](architecture.md) · [技术选型](tech-stack.md) · [地基实施清单](foundation-plan.md)

## 1. 项目目标

Traceleaf 是一个桌面优先、可恢复、可追踪、上下文隔离的递归任务运行时。每个 Task 聚焦一个明确问题，按需装配 Skill 与 Tools，通过明确结果与证据返回父 Task。

同一根任务树仅一个节点活跃。父任务委派后挂起，子任务交付后父任务恢复，逐步推动整体目标完成。任务树随执行生长，不要求开始前生成完整计划。

长期链路：递归探索 → 验证成果 → 记录依赖 → 提取并参数化 Workflow → 新输入验证 → 版本化复用 → 未来由 Storyloom 等产品消费。

## 2. 已确认的产品约束

| 约束 | 含义 |
| --- | --- |
| 本地桌面优先 | CLI 先验证，Electron 后封装；网页不是首版前提 |
| 同根串行 | 不自动识别安全并行，不引入并行审批门禁；不同根任务并发暂不承诺 |
| 单 Loop 有限 | 限制步数、时间、费用与重复失败 |
| 大任务可持续推进 | 不以固定深度或节点数默认终止；额度不足可保存进度并暂停 |
| 拆解要求进展 | 子任务有明确输入、交付与完成条件；Loop 耗尽不自动递归 |
| 上下文独立 | 父子通过显式输入、产物和证据交接，不自动共享完整历史 |
| 能力版本稳定 | 优先在创建任务时装配；动态申请后续增加 |
| 验证有证据 | 程序检查优先，决策模型辅助；模型自述不等于完成 |
| 恢复考虑外部副作用 | 结果未知时先核对，不承诺端到端恰好执行一次 |
| Workflow 与聊天解耦 | 导出流程不依赖原探索会话，TS 执行器调度实际计算工具 |

用户可设置总体费用上限和截止时间。结构允许持续递归，不意味着每次执行或本机资源没有限制。暂停、取消与运行故障均保留已完成成果和可解释记录。

## 3. 推进方法

按可运行的纵向闭环推进，不先实现所有抽象。每个阶段结束交付演示、关键验证、已知限制与下一阶段估算。

阶段编号在所有文档保持一致。日志、关联 ID、操作意图、产物来源和用量记录从早期加入，完整界面与高级提取器后置。工作量在阶段 1 完成后依据实际进度估算，当前不承诺固定总工期。

CLI 的命令模块、进程控制、输出与逐阶段验收单独维护在 [CLI 模块计划](cli-plan.md)，复用本计划的六阶段编号。

## 4. 六个阶段与验收

### 阶段 1：单 Task 闭环（当前下一步）

通过 CLI 提交一个小任务，运行固定能力集合，产出可检查的结果。使用 SQLite 和本地文件，接一个真实模型；同时保留假模型/工具稳定测试执行分支。

交付：最小契约、数据库迁移、ContextBuilder、ModelGateway、ToolRegistry、ToolExecutor、TaskRunner、基础验证与记录。

验收：可完成一次任务；工具错误、无效输出和步数耗尽有明确处理；两种模型输出模式通过适配验证；密钥不进入上下文和日志。不要求此时完成中断恢复或桌面界面。

### 阶段 2：串行父子任务

加入子任务创建、能力绑定、独立上下文、根执行权、挂起与返回。父任务接收并审查 A 后，再决定是否委派 B。

验收：同根不会有两个节点同时推进；结果与证据可被父任务消费；子任务不自动读取父任务或兄弟历史；重复通知不会重复汇总。

### 阶段 3：可靠恢复

补齐检查点、过期执行者保护、未知操作核对、暂停/恢复/取消、输入等待和用量结算。

验收：在关键位置主动结束进程再启动后可恢复；写操作不被盲目重做；未知费用保留待核对；用户设置的额度不足时暂停续跑。无进展触发调整或返回，不自动生成同义任务链。

### 阶段 4：桌面封装

用 Electron + React 复用核心运行时，提供任务入口、运行过程、交付结果三个视图。主进程管理窗口与生命周期，独立进程承载核心；界面经受控 IPC 操作核心。

验收：无需终端完成一次任务；可查看活跃节点、产物和费用；支持暂停、退出、重启恢复。验证安装包、用户数据路径和数据库迁移；目标发布系统及分发工具在阶段入口确定。

### 阶段 5：真实业务线路

优先接入 blender-vse MCP，选定小范围字幕时间线检查与修改场景，覆盖外部资源版本及实际工程验证。需要语义判断时试验 Jev/Laya，用自有样本评测。

验收：形成可重复演示的完整案例；能解释失败原因；版本冲突不会覆盖用户修改；关键故障场景能够恢复或明确暂停。持续积累成功率、成本、耗时与验收误判样本。

### 阶段 6：第一条可复用 Workflow

先人工辅助整理真实成功轨迹：保留必要步骤、明确数据依赖、参数化输入、生成版本化 IR，由自有 TS 执行器串行运行。随后再逐步自动化提取。

验收：脱离原始聊天历史，在同类新输入上运行；保留验证与异常处理；对比探索模式的模型调用次数、成本和耗时。单次重放成功不足以发布通用流程。

## 5. 第一条端到端里程碑

阶段 1–3 使用受控的结构化字幕工程与本地工具，优先证明运行时成立。阶段 4 提供产品入口，阶段 5 替换为真实工程与 MCP，避免过早让外部环境问题掩盖运行时缺陷。

场景：根 Task 委派 A 检查问题；A 交付清单后父 Task 恢复审查；再委派 B 修正并验证；最终交付工程版本、报告和证据。

必须可以导出任务树、上下文引用、模型与工具操作、产物依赖、验证报告和用量记录。完整故障注入清单见 [地基实施清单](foundation-plan.md)。

## 6. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 拆解无进展 | 比较目标、输入、方法与交付变化，返回父任务调整 |
| 上下文增长与缓存下降 | 任务内版本稳定；长结果外置；在检查点重建并保留来源 |
| 评审模型误判 | 明确问题与证据，领域样本校准；保留程序检查与人工核验样本 |
| 写入成功但回包丢失 | 操作 ID、幂等或状态核对；无法确认时暂停 |
| 资源被外部修改 | 写入前检查资源版本；树内串行不代表环境静止 |
| 桌面数据库或产物损坏 | 短事务、一致性备份、迁移记录、内容哈希与孤立文件核对 |
| 界面或数据库阻塞 | 运行进程与界面分离；测试驱动行为，测量后优化 |
| 平台打包不兼容 | 尽早验证依赖与 Electron ABI，阶段 4 明确支持平台 |
| Workflow 过度泛化 | 新输入、失败路径与版本依赖验证后发布 |

## 7. 暂缓事项与扩展条件

- 动态能力申请：创建时装配稳定后再做，区分授权、当前工具与历史残留。
- World Engine / RAG：先确定具体查询、事实来源、时间/分支语义和评测集。
- Storyloom：保持独立；Workflow 契约与执行稳定后再集成。
- 云服务、PostgreSQL、队列：出现明确远程、多用户或派送需求后单独规划。
- Rust：原生需求或测量到的计算瓶颈出现后评估，不预先重写执行器。
